WHAT I FOUND IN THE ACTUAL CODEBASE
===========================================================

This is not a general assessment. This is what I read in the code.

---
CRITICAL BUG 1: Voice Notes Fail 100% of the Time
---

Twilio has a hard 15-second webhook timeout. If the server does not respond within 15 seconds, Twilio marks the request failed and may retry it.

Whisper-1 voice transcription takes 20-38 seconds end-to-end (file download + transcription + GPT processing + Twilio response).

The current code does all of this sequentially inside the webhook handler. It will never finish in time. Every single voice note sent by every user currently gets no response. The user thinks Coach K is broken.

The code has a timeout wrapper set to 25 seconds. That is 10 seconds over Twilio's limit. It does nothing useful.

---
CRITICAL BUG 2: Database Dies at 80-100 Concurrent Users
---

There is a function called buildPatternSummary(). It runs on every single incoming message — not once per session, once per message. It fires 5 separate database queries each time it runs.

Railway PostgreSQL has a hard limit of 100 connections.

At 80 concurrent users each sending a message: 400+ database connections attempted simultaneously. PostgreSQL refuses new connections. All users get errors simultaneously.

There is no Redis cache. There is no pgBouncer connection pooler. There is no protection against this.

---
CRITICAL BUG 3: No Retry Logic on OpenAI Failures
---

When OpenAI returns a 429 rate limit error, the code fails immediately and returns nothing to the user. There is no exponential backoff. There is no retry.

At evening peak hours (17:00-21:00 SAST) when users are most active, OpenAI rate limits will be hit. Users get silence. Twilio may retry the webhook, causing duplicate processing and double API charges.

---
ADDITIONAL ISSUE: Weekly Scheduler Fires All Messages at Once
---

The weekly proactive message scheduler loops through all users and sends messages in a tight synchronous loop. At 500 users, this attempts 500 Twilio API calls in seconds. Twilio rate-limits the delivery. Messages fail or are heavily delayed.

WHAT I AM GOING TO BUILD BEFORE MONDAY
===========================================================

---
Fix 1: Async Voice Queue (estimated 4-8 hours)
---

The Twilio webhook will immediately respond with an acknowledgment message ("Coach K is listening...") and return HTTP 200 to Twilio within 1 second.

The voice file URL will be pushed to a Redis-backed job queue (BullMQ).

A separate worker process will pick up the job, download the audio file, send it to Whisper-1, receive the transcription, pass it through the coaching pipeline, and deliver the response to the user via outbound Twilio API call.

The user gets a response in 25-40 seconds instead of silence. Twilio never times out again.

---
Fix 2: Redis Cache for buildPatternSummary() (estimated 3-5 hours)
---

A Redis instance will be added to Railway (one-click add-on, ~$5/month).

The buildPatternSummary() function will check Redis first. If a cached result exists for that user, it returns immediately with zero database queries.

If no cache exists, it runs the 5 database queries as normal, then stores the result in Redis with a 1-hour expiry.

When a user logs a new meal, workout, steps, or water, their cache entry is invalidated so the next call gets fresh data.

Result: 80-90% reduction in database queries. The 100-concurrent-user database collapse is prevented.

---
Fix 3: Exponential Backoff on OpenAI (estimated 2-3 hours)
---

Every OpenAI API call will be wrapped in a retry handler. If OpenAI returns a 429 rate limit error:
- Wait 2 seconds, retry
- If fails again, wait 4 seconds, retry
- If fails again, wait 8 seconds, retry
- If still fails, return a graceful fallback message to the user

This stops immediate failure on rate limit. It eliminates retry-duplication charges from Twilio.

---
Fix 4: Week 9 Retention Flow (estimated 2-3 hours)
---

On day 56 (end of Week 8), the system will send a message offering two paths:

Option 1 — Maintenance Phase: 3 days/week, sustain results
Option 2 — Advanced Phase: 5 days/week, new exercises, higher intensity

User picks one. The programme continues indefinitely. The churn cliff is eliminated.

---
Fix 5: Throttled Proactive Message Queue (estimated 3-4 hours, after Redis is running)
---

The weekly scheduler will push all messages into a BullMQ queue instead of firing them in a synchronous loop.

The queue will process at a controlled rate of 10 messages per second. 500 users = 50 seconds to complete delivery. Twilio rate limits are never hit. All messages deliver successfully.

---

- Pricing (stays at R149)
- Core coaching logic and AI prompts
- Payment flows
- Onboarding flow
- Any database schema changes
